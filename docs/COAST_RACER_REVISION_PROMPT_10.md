# COAST RACER 改修プロンプト10

作成日: 2026-09-27。
基準: 改修9／公開Build `44db0ee151c0`、実装コミット `4da8cb9`、公開確認コミット `8b290cb`。

この文書を新規改修の指示として使用する。過去のプロンプトは上書きしない。今回の依頼はプロンプト作成までであり、実装・push・Azure公開は別途実行指示を受けてから行う。

## 1. 目的

「湘南海岸」を「湘南海岸コース」に改称し、江の島をモチーフにした起伏のある八の字、島の裏側から入る洞窟、海岸・砂浜・烏帽子岩、市街地・江ノ電、道の駅、高速道路を順に体験できるコースへ改修する。
車体選択画面には、指の横スライドで前後の車体へ切り替える操作を追加する。

## 2. 確認ボックスで確定した仕様

ユーザーの回答により、以下を確定事項とする。

1. 高速道路の後は出口から一般道へ下り、一般道の新しいスタート地点に戻る。
2. 島内の八の字の交差は、山側の道路と地下の洞窟で上下を分ける。
3. 道の駅は、海岸線から高速道路へ向かう右折地点の背景施設・目印として置く。敷地内走行は追加しない。
4. 高速道路走行中は基礎速度を＋50％にし、高速道路を降りたら通常へ戻す。本プロンプトでは「基礎速度」を、各車の素の最高速度として具体化する。詳細は第5.6節。

## 3. 維持する仕様と変更範囲

- COAST RACER、日本語初期設定、スマホWeb、2周、最大8台、全10車種、CPU5段階、昼夜、オンライン、30ミッション、端末内プロフィールを維持する。
- 高速道路内の速度補正を除く既存の車体性能、スペシャル、報酬、アイテム装着、四輪配置、星・月・太陽、ゴール演出、入力解除処理を退行させない。
- 追加のユーザー指示により、約600m手前というスタート位置の制約を解除する。高速道路が短くなりすぎないよう区間配分を優先し、スタート／ゴールと8台のグリッドは一般道の安全な直線へ配置する。
- 1周4～5kmを維持し、島内・海岸・高速道路の区間配分を調整する。実在の地理を縮尺どおり再現することより、特徴と走りやすい周回構成を優先する。
- 往路は橋の東側、復路は西側。既存の中央仕切り、橋床・橋脚、シーキャンドルを維持する。設計上の南は本土から島へ向かう方向で、UIへ方位説明は追加しない。
- 灰色路肩は減速のみ・警告なし。芝生逸脱時だけ5秒警告し、直前に走行した道路区間の中心へ復帰する。洞窟壁や高速道路の防護柵への接触を、芝生侵入として扱わない。
- 山岳・鈴鹿のコース形状は今回の変更対象にしない。共通描画・操作処理を変更する場合は両コースも回帰確認する。
- Azure App Service Free／SQL Database Freeのみの構成を維持する。
- `Assets/Scripts/CarController.cs` の既存ユーザー変更は上書き・無断で取り込まない。
- 新規インストールが必要なら名称・バージョン・用途を記録する。空き容量1GiB未満または中断指示があった場合は、進捗を保存して中断する。

## 4. 名称の統一

- 日本語のコース名を「湘南海岸コース」に統一する。
- コース選択、マルチプレイのロビー、レース結果、記録、ミッションや報酬のコース名参照など、利用者に表示する箇所を確認する。
- 英語モードでは意味が対応する名称（Shonan Coast Course）とし、言語切替を維持する。
- 内部コースID `shonan` と表示名を区別する。名称変更だけを理由にプロフィールや累計記録を消さない。
- 今回は経路そのものも変わるため、旧コースのタイムとの分離は第9節に従う。

## 5. コースの順路

確定した一続きの周回路:

スタート／ゴール
→ 本土の直線区間
→ 橋の東側から島へ
→ 山を上る八の字の地上側ループ
→ 島の裏側へ下る
→ 裏側の岩屋をモチーフにした洞窟入口
→ 山道の下を通る洞窟側ループ
→ 島の橋側へ出る
→ 橋の西側で本土へ戻る
→ 海岸線を西へ走る
→ 道の駅を目印に右折
→ 上りランプ
→ ETCゲート
→ 高速道路
→ 出口ランプで一般道へ下る
→ 市街地・江ノ電並走区間
→ スタート／ゴール。

海岸区間にも海沿いの街並みや鉄道の存在が分かる景観を置き、帰路の一般道では江ノ電との並走がはっきり体験できるようにする。区間の接続で急な直角折れ・車線の逆転・行き止まりを作らない。

### 5.1 江の島の八の字と山道

- **島内の走行経路そのもの**を平面図で八の字と読める形にする。コース全体だけが八の字だったり、島内が単純な円周のままだったりする実装は不可。
- 島に入ってからまず登坂し、中央の丘とシーキャンドルが見える山道を走る。その後、島の裏側へ下り、洞窟へ入って橋側へ戻す。
- 八の字は一方向の連続した経路とし、交差点で進路選択を要求しない。確定仕様では地上道路と洞窟を高さで分離し、同一平面の交差衝突を作らない。
- 上下の路面の間には、車体・装飾品・追従カメラが干渉しない空間を確保する。海上や空中へ露出する構造は橋脚・橋床等で支え、地形に埋まる部分は岩盤と自然につなぐ。
- 勾配の始終点を滑らかにつなぎ、全10車種で底打ち・タイヤ浮き・登坂不能・出口の急激な跳ねがないこと。
- 鳥瞰図と高低差の図で、八の字の二つのループ、上下の交差、洞窟入口／出口、橋への合流を確認可能にする。

### 5.2 島の裏から入る洞窟

- 江の島岩屋の岩壁や海食洞窟をモチーフにする。実在の岩屋を車で貫通できる道路として事実再現する指示ではなく、ゲーム用の走行洞窟として構成する。
- 橋と反対の島の裏側に入口を置き、岩場・海・洞口が走行中に分かるようにする。山の表側に通常のトンネルを置くだけで代用しない。
- 洞窟を通過すると橋側へ戻れる。行き止まりや強制ワープでルートをつながない。
- 岩壁・天井・内部路面・入口の厚みを作り、外の空や山が壁を通して見えたり、天井の裏面が消えたりしないようにする。
- 追従カメラとバックミラーが壁を突き抜けないこと。必要に応じてカメラの距離を滑らかに調整し、出口で急に飛ばさない。
- 昼も洞窟内に陰影をつけ、夜はヘッドライトと少量の固定照明で走路を把握できるようにする。太陽・月・星・海面が洞窟の手前へ重ならないこと。
- 通路幅と天井高は8台レースと既存車種・装飾品を考慮する。柱や岩を路面に突き出して詰まりを作らない。
- 洞窟断面や路肩の処理は明確な区間情報で制御する。既存の「道路周辺を削る」地形生成処理が、洞窟の天井や上段の道路を消さないようにする。

### 5.3 海岸・砂浜・烏帽子岩・市街地・江ノ電

- 海岸線を走る際、海側には海と連続する砂浜、沖には特徴的な烏帽子岩を配置する。陸側には市街地を配置し、海と街の間を走っていることが分かる構成にする。
- 烏帽子岩は遠景として認識できる形と大きさにする。道路近くの単なる球体や不自然に巨大な岩にしない。
- 江ノ電を模した電車・線路・架線や沿線景観を配置する。少なくとも一部でレース車と電車が並走する様子を見られること。
- 鉄道は道路と安全に分け、電車や架線柱が走行路へ突き抜けないこと。高速道路から下りた一般道と市街地の配置も自然につなぐ。
- 海岸・砂浜・烏帽子岩、市街地、江ノ電をそれぞれ通常の走行視点で確認できる区間を用意する。鳥瞰図でしか見えない小物配置にしない。

### 5.4 右折地点の道の駅

- 海岸線を離れ、高速道路へ向かう右折地点に「道の駅 湘南ちがさき」をモチーフにした施設を配置する。
- 確定仕様では、施設は右折の目印となる沿道景観。建物、看板、駐車場、植栽などで道の駅と分かるようにする。
- 道の駅は右折する前から自然に見える位置とし、建物や看板でコーナー出口を隠さない。ゲーム画面に長い施設説明は追加しない。
- 既存の曲がり角に看板だけ置いて済ませず、沿道のまとまりとして作る。駐車車両等は共有モデルや簡略形状を使い、描画負荷を抑える。

### 5.5 上りランプ・ETC・高速道路

- 海岸線から右折した後、上りランプで高度を上げ、ETCゲートを通って高速道路の本線へ入る順序にする。
- ETCはレース演出として扱い、支払い・アカウント・通信認証は不要。通過で車を停止させない。開閉バーを付ける場合は車を挟まない。
- ゲートの有効幅・高さは大型車、バナナボート、バイク、装着アイテムを考慮する。8台が来てもCPUが入口で詰まらない構成にする。
- 高速道路は一般道と見分けられる舗装、車線、中央分離帯、側壁、防護柵、案内板、橋脚を配置する。
- 短い料金所だけで高速道路区間を表現せず、加速と追い越しを楽しめる連続した区間を設ける。本線は約1kmを設計目標とし、少なくとも900mを確保する。入口／出口ランプを本線長へ含めず、完成時に実測距離を報告する。
- 確定仕様では出口ランプから一般道へ下り、江ノ電のある市街地経由でスタート地点へ戻る。
- 高架下、橋脚と地面の接続、ランプ合流を点検し、宙に浮いた板状道路や地面を貫く柱を残さない。

### 5.6 高速道路内の基礎速度＋50％

- 高速道路の走行区間にいる間だけ、車種ごとの素の最高速度を **1.5倍** にする。例えば通常の素の最高速度が200km/hなら、高速道路内の基礎最高速度は300km/hとなる。
- 速度計の表示だけを増やすのではなく、走行シミュレーションの速度上限へ反映し、実際に高速走行できること。現在速度を入場時に突然1.5倍へ跳ね上げる処理にはしない。
- 車種カタログの保存値・選択画面のステータス・重さ・加速・グリップは変更しない。最高速度の基準値と区間補正を分け、通常の加速により高速道路用の上限へ到達する。
- 適用区間の初期設計は、ETC通過後の本線合流から出口分岐まで。入口／出口のランプは通常区間とし、どこから1.5倍になり、どこで戻るかを経路図と区間データに明示する。道路の見た目と効果境界を合わせる。
- 出口では基礎最高速度の補正を直ちに1.0倍へ戻す。現在速度は通常の速度制限・減速処理で滑らかに収束させ、強制停止や突然の速度切断を起こさない。
- 高速道路からコース外へ逸脱した場合は補正を継続しない。復帰時は復帰先の区間から再計算する。再戦、リセット、メニュー復帰、切断／再接続で補正が残らないこと。
- ルートの区間・進行位置・高さ・道路内判定を使う。同じ平面座標にある高架下の一般道や洞窟に、誤って高速道路補正が掛からないようにする。
- 全10車種、人間、CPU、シングル、オンラインに同じ補正を適用する。オンラインの速度・走行区間はサーバーと共有ロジックで判定し、クライアント申告だけを信用しない。
- 毎フレーム現在の上限へ1.5を掛け続けて累積させない。毎回「元の車種の基準値 × 区間倍率」から計算し、何周しても増幅しないこと。
- スペシャル・スリップストリーム・妨害等の既存補正は、高速道路の基礎最高速度と合成する。既存効果の意味や時間を変えず、二重適用を防ぐ。計算順序を実装記録に示す。
- CPUのコーナー速度や衝突判定まで無条件に1.5倍にしない。直線では高速域を利用し、カーブや出口では必要な減速を行う。速度増加で路面・コイン・ゲート・ゴールをすり抜けないこと。
- 車体選択画面の基本ステータスは従来どおり。レース中の速度計は実際の速度を表示し、300km/h等の高速域でも数字や針が破綻しないよう確認する。

## 6. 立体構造・周回・復帰の整合

- 走行中心線、路面モデル、Blender地形、コリジョン、カメラ判定、ミニマップ、チェックポイントを同じ経路データに基づいて生成する。
- 八の字の交差、洞窟の上と下、高速道路と一般道、橋の往復車線を平面距離だけで判別しない。進行順序と高さを考慮し、別の区間へ進行インデックスや接地先が飛ばないようにする。
- 初回のスタートライン通過は周回に数えず、必須区間を順に通ってから周回を成立させる。逆走や交差地点の横切り、コース復帰で周回数が増えないこと。
- 2周目は実際のゴールラインを正規方向へ越えた時点で終了する。洞窟や高速道路の新設により最後のチェックポイントが未通過扱いにならないこと。
- 復帰先は逸脱前の正しい道路区間の中心と向きにする。洞窟から山道へ、上段から下段へ、橋の往路から復路へ移動させない。
- 1周3枚の共有コインはカーブのアウト側へ配置し直す。壁・天井・柱に埋めず、上下の別区間から取得されないこと。取得後2秒復活とオンライン共有を維持する。
- CPUも同じ経路を走り、洞窟・ETC・高速道路出口の幅や勾配に応じて操舵・速度を調整する。今回の変更を理由に既存の車体性能やCPU5段階の意味を変えない。

## 7. 車体選択のスワイプ

### 対象と操作

- シングルプレイの車体選択と、マルチプレイのロビーから開く車体選択の両方に適用する。ホスト／参加者とも、自分の車体だけを変更する。
- 車体プレビュー領域を左へスワイプすると次の車体、右へスワイプすると前の車体へ切り替える。末尾と先頭は循環させる。
- 一度のスワイプで1台だけ切り替え、指を離すまで複数台を飛ばさない。切り替えは短く滑らかな横移動・フェード等で表現する。
- 誤操作を避けるため、横移動量が一定以上で縦移動より明確に大きい場合に成立させる。初期案は40 CSS px以上かつ横移動が縦移動の1.3倍以上。実機相当のタッチ試験で調整してよい。
- 小さな指の揺れ、タップ、縦スクロールでは切り替えない。画面全体をスワイプ領域にせず、戻る／決定／設定、音量スライダー、アイテム配置等の操作から開始したジェスチャーは対象外にする。
- 既存の車体ボタンによる選択とマウス操作を維持し、スワイプを唯一の選択手段にしない。

### モデル回転との使い分け

- 現行の `club.js` は `orbitSurface` の横ドラッグをモデル回転に使っている。同じ入力で回転と車種変更を同時に実行しない。
- **車体選択画面のプレビューはスワイプによる車種変更、図鑑のプレビューは従来の360度回転**という使い分けを基本案とする。
- 図鑑の装飾編集や色・位置調整のジェスチャーを壊さない。図鑑へ車種切替スワイプを今回一律適用しない。

### 状態と通信

- モデル、車名、各ステータスバー、スペシャル名・説明、選択状態、保存された車種を一貫して更新する。
- Pointer Events等で指を追跡し、`pointerup`、`pointercancel`、`lostpointercapture`、画面切替、非表示、設定を開く操作で確実に終了する。
- 連続スワイプや素早い往復でも二重確定・入力の固着・古いモデルの残存・不要なオブジェクト生成を起こさない。
- 長押し選択やダブルタップ拡大を防ぐ既存処理を維持する。縦スクロールの必要な領域まで全面的に無効化しない。
- マルチプレイは、成立した車種変更を既存の選択処理と同じ経路でサーバーへ通知する。移動イベントごとに通信しない。
- 準備完了後の変更は既存の準備解除・ロビー同期ルールを維持し、開始済みレースの車種がスワイプで変わらないこと。

## 8. 描画負荷

- `docs/REVISION_9_PERFORMANCE_AUDIT.md` を先に読み、改修9の負荷と測定限界を基準にする。ブラウザーのrequestAnimationFrame頻度をUnityの描画FPSとして報告しない。
- 洞窟・道の駅・高速道路の追加で、見えない景観まで常時処理する量を増やしすぎない。共有材質・共有メッシュ、適切な区間分割、遠景の簡略化を優先する。
- 特に洞窟内では不要な外部景観、地上では見えない洞窟内装の省略を検討する。出口の直前で背景が突然出現する状態は避ける。
- 洞窟の固定照明を多数のリアルタイムライトで作らない。既存ヘッドライトとの組み合わせ、発光材質、軽量な陰影等で雰囲気と視認性を両立する。
- 改修前後で同じ端末・画質・解像度・台数・測定方法を用い、海岸、山道、洞窟、ETC、高速道路、昼夜を確認する。目標は軽量設定で30 fps相当を維持すること。未達なら原因・調整・残る制約を報告する。
- ソフトウェア描画、PC GPU、スマホ実機の結果を区別する。実機がない場合は、iPhone／Galaxy／Pixel相当の画面・タッチ確認を模擬検証と明記する。

## 9. 新旧コース記録
